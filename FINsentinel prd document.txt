1. EXECUTIVE SUMMARY
--------------------------------------------------------------------
Traditional financial fraud systems rely on static, row-by-row database checks that evaluate transactions in isolation[cite: 1]. FinSentinel is a B2B SaaS web application designed to track and visualize financial crime across scattered patterns. By converting raw transaction logs into a queryable graph network, FinSentinel detects multi-account laundering loops, smurfing activities, and mule networks in real time. For this hackathon, FinSentinel will be delivered as a focused prototype utilizing simulated datasets to demonstrate the core algorithmic feasibility[cite: 1].

2. PROBLEM STATEMENT CONTEXT
--------------------------------------------------------------------
This product directly addresses Problem Statement 5: Tracing Financial Crime Across Patterns, as outlined in the "Build $ Bank" guidelines[cite: 1]. 
* The Challenge: The most damaging financial fraud rarely occurs in a single transaction; it is deliberately spread across numerous small transfers and accounts to avoid static threshold detection, outpacing human analysts' ability to manually trace the funds[cite: 1].
* The Objective: To spot deliberately scattered transactional patterns, connect the dots, and define an actionable escalation process once flagged[cite: 1].

3. PRODUCT VISION & TARGET AUDIENCE
--------------------------------------------------------------------
* Vision: To become the standard plug-and-play graph analytics API for the mid-tier financial ecosystem, reducing false positives and accelerating AML (Anti-Money Laundering) investigations.
* Primary Audience: Compliance Officers and Risk Analysts at mid-tier NBFCs, Neo-banks, and UPI Payment Aggregators.
* Secondary Audience: System integrators building backend infrastructure for emerging digital loan apps.

4. TECHNICAL ARCHITECTURE & STACK
--------------------------------------------------------------------
As a solo developer prioritizing speed and impact, the stack is entirely Python-based, merging backend logic and frontend rendering into a unified application.
* Language: Python 3.9+
* Frontend Framework: Streamlit (Customized with Cyberpunk/SOC CSS for a high-tech UI).
* Graph Engine & Analytics: NetworkX (for in-memory mathematical graph processing).
* Data Visualization: PyVis (for rendering interactive HTML network graphs).
* Data Manipulation: Pandas (for parsing CSV datasets and tabular data rendering).

5. CORE FEATURES & FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------
5.1. Data Ingestion Module
* Requirement: The system must accept tabular transaction data and instantly map it into nodes (Accounts) and edges (Transfers).
* Hackathon Scope: Per the "Build $ Bank" guidelines, the system will not integrate live bank APIs; instead, it will ingest a simulated or publicly available CSV dataset[cite: 1]. 
* Data Schema Expected: Transaction_ID, Sender_Account, Receiver_Account, Amount, Timestamp, Device_ID.

5.2. Graph Detection Engine (The Algorithms)
The core backend must execute three specific analytical checks on the ingested data:
* Velocity & Smurfing Detection: The engine must flag "Node A" if it distributes funds to > 5 temporary accounts within a 10-minute window, and flag "Node Z" if it receives accumulated funds from those temporary accounts shortly after.
* Multi-Hop Traversal (Cycle Detection): The engine must use Depth-First Search (DFS) to identify circular fund flows spanning 3 or more intermediate hops.
* Entity Linkage: The engine must group seemingly unrelated accounts if they share identical metadata (e.g., same Device_ID or IP subnet).

5.3. Real-Time SOC Dashboard (User Interface)
The UI must mimic a Bank Security Operations Center (SOC) terminal.
* Dark Mode / Cyberpunk Aesthetic: Pitch-dark background with neon green and red accents.
* Live Metrics Row: Displaying "Total Transactions Scanned," "Active Nodes," and "Mule Chains Detected."
* Interactive Visualizer: A central canvas where the network graph is rendered. Normal accounts are displayed in cyan/blue, while flagged mule loops glow bright red.
* Terminal Logs: A scrolling text box mimicking live console logs, showing the engine's step-by-step processing and alert generation.

5.4. Actionable Alerts & Escalation
* Requirement: The system must define an action process once a pattern is flagged[cite: 1].
* Execution: Below the visualizer, a data table will dynamically populate with the isolated mule chain. It will assign a composite "Risk Score" (e.g., 98%) and simulate an automated API trigger (e.g., "Status: Auto-Frozen").

6. DETAILED UI LAYOUT (WIRE FRAME)
--------------------------------------------------------------------
* Top Navigation & Header: Title (FINSENTINEL // GRAPH ENGINE) and Status Badge.
* Section 1: The Metrics Banner (Four key KPI cards).
* Section 2: The Command Center.
  - Left Column (30% width): System Console (scrolling logs) and Critical Threat Card.
  - Right Column (70% width): Network Graph (PyVis interactive HTML component).
* Section 3: The Audit Trail. Flagged Breakdown via a Pandas dataframe.

7. SCOPE & HACKATHON LIMITATIONS
--------------------------------------------------------------------
* No Live Databases: The prototype will run in-memory using NetworkX rather than deploying a heavy instance of Neo4j.
* Simulated Data: The product will strictly utilize a custom-generated synthetic CSV infused with deliberate fraud loops to effectively demonstrate the core idea without external dependencies[cite: 1].
* Focused Prototype: The goal is not to present a fully production-ready AML compliance suite, but a focused, technically feasible prototype demonstrating how graph logic outperforms linear SQL logic[cite: 1].

8. BUSINESS & SCALABILITY PLAN (30% FOCUS)
--------------------------------------------------------------------
* Monetization: A tiered B2B SaaS model. A Freemium tier for testing, a Volume-based API pricing tier ($0.001 per risk check), and a fixed Enterprise Dashboard license for compliance teams.
* Future Scalability: Post-hackathon, the in-memory NetworkX engine will be migrated to Amazon Neptune or Neo4j, enabling the ingestion of millions of live Kafka streaming events. Machine Learning modules will be introduced to predict novel fraud topologies before human analysts define the rules.
